# 功能开发与验收

先明确用户目标和必要行为，再实现并逐项验收。Agent 起草记录、调查事实和执行验证；已有决定继续有效，只有未确定的产品取舍需要用户回答。

## 开发记录

| 类型 / 文件 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 意图 [intent.md](templates/change/intent.md) | 为什么做，怎样才解决了原问题？ | 用户问题、目标、范围、约束、需求来源 |
| 规格 [spec.md](templates/change/spec.md) | 功能应当怎样工作？ | 入口、前提、操作、结果、失败处理和验收要求 |
| 计划 [plan.md](templates/change/plan.md) | 怎样把规格做出来？ | 实现顺序、改动位置、依赖、测试步骤和剩余工作 |
| 验收 [verification.md](templates/change/verification.md) | 实际做到了什么，有什么证据？ | 每条要求的实现情况、实测结果和未通过项 |

同一功能的四份文件放在一起，不分别散落到全项目的 intent、spec、plan 目录。例如：

```text
zeta-code/docs/changes/<工作名>/
  intent.md
  spec.md
  plan.md
  verification.md
```

意图不写实现步骤，规格不写施工进度，计划不复制整份规格，验收不把“准备测试”写成“已经通过”。用链接和 AC 编号关联四份记录；计划全部勾选只能说明步骤做完，完成结论仍要对照意图和规格验收。

长期文档另行维护：`capabilities.md` 说明当前功能和缺口，`design/` 说明架构，`spec/` 保存按主题持续维护的行为规格，README 说明入口和开发方法。开发中的 `changes/<工作名>/spec.md` 描述本次变化，完成后把有效要求合入对应长期规格，避免同时维护两份现行规则。已有文档位置由所属项目索引映射，不要求其他项目为统一形式批量搬迁。

A 类小修复可在任务中合并记录。B 类新功能保留四份文件；C 类架构或兼容性变更还需在规格中说明责任、接口、状态、持久化及恢复影响，并在实现前审查设计。分类依据是目标契约的变化，恢复已有行为不会因为涉及状态或持久化就自动属于 C。

记录放在 `<所属项目>/docs/changes/<工作名>/`，TUI 使用 `zeta-code/docs/changes/`；没有单一产品负责的跨产品工作使用根 `docs/changes/`。在所属项目索引登记入口，恢复同一工作时继续原目录。已有 Issue 或文档承担相同职责时引用其版本，不复制正文。

## 写代码前

意图必须说明用户最终能完成什么。规格用 `AC-1` 等编号记录“前提、动作、结果”；有必要时用 `INV-1` 记录始终应成立的约束。计划把这些编号对应到实现、产品入口和验证步骤。

从原始目标检查以下场景，发现必要漏项就补进规格：

- **开始与完成**：入口、初次使用、空数据、正常结果。
- **失败与取消**：输入错误、权限拒绝、超时、重试、重复操作。
- **切换与恢复**：页面、会话、连接切换，重启后的状态与旧请求处理。
- **使用环境**：支持的产品、平台、终端，以及适用的键盘、鼠标、窄窗口和资源限制。

只记录实际适用的要求和容易误判的排除理由。未知项写清阻塞范围；事实由 Agent 调查，产品取舍由用户决定。不要在交付时将未完成的必要行为改成非目标。

## 验证

每条 AC 和适用的 INV 分别记录实现情况、实际证据和验证结果。实现状态可为已实现、部分实现、未实现或待核实；验证结果可为通过、失败、尚未验证或不适用（附理由）。测试文件存在或编译通过不能代替行为验收。

按[测试规范](../.github/instructions/testing.instructions.md)运行受影响行为和构建的最小检查。Web、Electron 使用 Playwright；TUI 使用状态、事件、协议、字符输出和真实 PTY 场景。重要功能与架构变更应独立审查；实际只有自查时如实记录。

验收记录保存意图和规格版本、Git 基线及相关未提交差异、命令、环境和结果。已有工作区修改时，只写 HEAD 不足以标识候选。不要让记录代码指纹的证据文件参与该指纹计算。

## 恢复与完成

恢复前核对上游版本、当前代码和未完成项。意图或规格变化后重查受影响的计划与验证；行为代码、测试或运行配置变化后，相关通过结论失效。纯文档纠错只重查文档。

完成需同时满足：

1. 原始目标得到满足，必要行为没有遗漏或被临时排除。
2. 必要验收项、相关构建与检查均通过；失败或尚未验证的必要项保持未完成。
3. 受影响的能力状态、长期约定和代码入口已更新，限制与审查范围已记录。

完成后保留可追溯的约定和验证证据，再删除过期工作记录及索引引用；未完成目标继续保留。文档更新范围遵守[写作规范](documentation-guidelines.md)。

此流程借鉴 Development Workflow Kit v0.12。`/develop` 自动化仍属于[产品设计](develop.md)，使用这些记录不代表该命令已经实现。
