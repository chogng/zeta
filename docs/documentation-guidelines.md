# 文档写作规范

文档帮助读者完成任务：理解行为、修改实现或判断结果。开头直接说明用途或结论，随后只写完成这件事需要的信息。

## 内容放在哪里

沿用 Development Workflow Kit v0.12 的文档分工；下表映射到 Zeta 现有文件，不要求每个目录新建一整套文档。

| 内容 | 放置位置 |
| --- | --- |
| 模块用途、必要入口和运行命令 | 相邻 README；crate 职责用不超过三点说明 |
| 当前功能、支持范围和已知缺口 | 产品能力表或已有功能文档，链接到详细依据 |
| 稳定的责任边界、接口约定、生命周期和重要取舍 | 所属项目的架构设计文档（design） |
| 按功能维护的操作、布局、样式和可观察行为要求 | 所属项目的行为规格（spec）；未实现的要求就地标明 |
| 关键代码入口、注册方式、测试与调试方法 | 现有实现指南；内容很少时留在 README |
| 一次开发的目标、规格、步骤和验收结果 | 同一工作目录中的 intent、spec、plan、verification，分工见[开发记录](development-workflow.md#开发记录) |
| 缺陷复现、局部算法与历史决定 | 测试、必要的代码注释、Git 或原任务 |

同一事实只详细解释一次。引用方保留足以理解当前内容的一句话和链接；读者不应为一个简单问题连续跳转多份文档。只有主题、读者或维护责任可以独立时才拆文件。

## 怎么写

- **直接进入主题。** 不强制“快速理解”、职责声明、状态头、术语表或总结。只有会发生误读时，才补一句范围或状态说明。
- **按问题组织。** 使用“运行测试”“断线恢复”“添加命令”等具体标题。短文可以没有二级标题。
- **保留关键细节。** 写出会影响操作或判断的条件、限制和原因。代码入口只列关键位置，不逐项抄录私有类型、函数、文件树或测试名称。
- **用合适的表达。** 步骤用编号列表，同维度比较用表格，复杂关系才画图。表格单元格需要长段解释时改用小节；不把同一信息再写成图、表和总结。
- **说清楚。** 中文正文用日常技术用语；代码标识符、命令、配置键保持原名。只解释可能产生歧义的术语，不机械添加中英对照。
- **让段落可读。** 一个段落说明一件事，一个语义段落占一个源码行。不要用分号、硬换行或 `<br>` 堆叠无关事项。

模板是起草提示，完成后删除占位说明、重复字段和无关章节。不要为了填满模板写“无”“不适用”或复述通用规则；验收中确需排除的场景应保留理由。

## 删除什么

删掉不会影响理解、操作或判断的段落，尤其是：

- “本文拥有……”“本文件不是……”等重复职责宣言和边界提醒；
- 引言、快速理解、导航表和总结对同一内容的重复；
- 从文件名或源码即可读出的接口清单、逐文件讲解；
- 每个专题都复制的单写者、测试、命名、文档更新等仓库规则；
- 修复经过、已完成迁移、没有实际需求的未来设想。

精简不能删除仍有效的约定、已知限制、执行命令或验证证据。长文先删重复内容，再按读者任务重组；不要通过增加索引、摘要或更多小文件掩盖正文问题。

## 什么时候更新

设计文档只在责任、接口、生命周期、持久化或跨组件约定改变时更新。普通修复用回归测试证明；文件移动只修复相关入口；文案和样式修改只更新受影响的行为或样式说明。不要因为改了一个目录，就同步重写它的全部文档。

当前实现以源码、协议和测试为准。计划在对应段落标明“计划”，缺口写明缺少的行为；不要给整篇文档反复加免责声明。测试入口与测试通过分别记录，未经执行不得写成通过，也不能补造旧功能的意图或验收历史。

新增或删除文档时更新所属项目索引；索引只列入口和简短用途。开发工作完成后，将有效约定和证据保留到长期文档、提交或原任务，再删除过期计划及引用。

提交前核对三件事：内容是否准确且必要，链接与命令是否有效，同一事实是否重复维护。纯文档修改运行相关文档检查，不为格式统一批量改写无关文档。
