# ZUI 样式系统设计

> 状态：Proposed
>
> 范围：本文只设计 ZUI 中样式的声明、作用域、组合、解析、校验与诊断。颜色、字体、尺寸等值由谁提供，不属于本文范围。

本文描述 ZUI 样式系统的长期形态，不是现有接口说明。当前可用接口见 [ZUI 声明式样式](zui-declarative-styles.md)，ZUI 的职责边界见 [ZUI README](../zui/README.md)。

## 1. 结论

ZUI 应提供接近 CSS 的书写体验：在组件内写节点，在节点内写属性和值；同时保留 Rust 的类型检查、明确归属和可追踪调用路径。

```rust
zui::styles! {
    pub(crate) FilesRowStyles {
        row surface {
            height: 24;
            gap: 8;
            align_items: center;

            text label {
                grow: 1;
                shrink: 1;
                min_width: 0;
                overflow: ellipsis;
            }

            row actions {
                shrink: 0;
                gap: 4;
            }
        }
    }
}
```

上面是目标语法示意，不承诺最终宏名。它表达五件事：

- `FilesRowStyles` 只属于 `FilesRow` 组件。
- `surface`、`label`、`actions` 是编译期生成的局部样式角色，不是运行时字符串。
- 节点嵌套表达局部归属：`label` 和 `actions` 位于 `surface` 子树。
- 节点种类决定可写属性；`text` 不能写容器布局属性，`row` 不能写文本截断属性。
- 数字字面量由属性类型决定含义；业务代码不需要先转成 `f32`。

## 2. 设计目标

| 目标 | 设计结论 |
| --- | --- |
| 像 CSS 一样容易写 | 组件内按“节点 → 属性 → 值”声明 |
| 层级能看懂 | 组件归属树和组件内样式节点树分开表达 |
| 写错尽早发现 | 名称、节点种类、单位和静态非法值在编译期报错 |
| 动态值安全 | 动态值必须先成为有约束的 Rust 类型，解析时再次校验 |
| 没有隐式覆盖 | 不提供全局层叠、祖先选择器和源码顺序优先级 |
| 宏不是另一套系统 | 宏和 builder 生成同一组类型并经过同一条校验路径 |
| 能定位问题 | 每个已解析属性保留组件、角色、属性和输入位置 |
| 大型界面可维护 | 组件边界隔离样式，父组件不能改写子组件内部角色 |

本文不设计：

- 颜色、字体、尺寸等值的存储位置和加载方式。
- 具体产品的视觉规范。
- 组件业务状态如何产生。
- 数据树、命令、焦点策略和交互流程。

这些内容可以向样式函数提供类型正确的输入，但不能改变样式系统自身的作用域和校验规则。

## 3. 两层树模型

大型界面不能只靠一棵扁平样式树。ZUI 使用两层树：组件归属树负责跨组件边界，局部样式节点树负责单个组件内部。

### 3.1 组件归属树

以文件浏览功能为例：

```text
Workbench
└── PanePart
    └── Files
        ├── FilesToolbar
        └── FilesTree
            └── FilesRow
                └── RowActions
```

每个组件开启自己的样式作用域。父组件可以：

- 决定子组件放在哪里以及占多少空间。
- 向子组件传递它公开接受的完整样式输入。
- 选择子组件公开的变体。

父组件不能：

- 使用字符串路径查找子组件内部节点。
- 改写 `FilesRow::label` 之类的私有角色。
- 依赖子组件内部又套了几层容器。

因此，从问题节点可以沿 `FilesRow → FilesTree → Files → PanePart → Workbench` 追溯归属；反方向却不能穿透组件边界写样式。

### 3.2 局部样式节点树

`FilesRow` 内部可以有自己的命名节点：

```text
FilesRowStyles
└── surface: row
    ├── label: text
    └── actions: row
```

嵌套表示“属于哪个局部子树”，不要求两个命名节点必须是直接父子。中间允许存在没有命名的实现节点。这样增加一个无名容器不会迫使样式改名，但把 `label` 移到另一个命名分支时会被检查出来。

每个角色带有三个编译期信息：

```text
角色 = 组件作用域 + 父角色 + 节点种类
```

所以，即使多个组件都有 `label`，它们也是不同的 Rust 类型。跨组件使用、跨分支使用或把文本角色绑到容器节点都会编译失败。

### 3.3 样式路径只用于诊断

开发工具可以显示：

```text
Workbench/PanePart/Files/FilesTree/FilesRow::surface/label
```

这条路径由已建立的组件实例和角色关系生成，只用于检查、日志和定位错误。ZUI 不在运行时解析这条字符串，也不会用它匹配节点。

## 4. 与 CSS 的对应关系

| CSS 概念 | ZUI 对应设计 | 边界 |
| --- | --- | --- |
| 类选择器 | 组件内的类型化角色 | 不能跨组件使用 |
| 后代关系 | 嵌套角色路径 | 由构建树验证，不做字符串匹配 |
| 属性声明 | 节点种类限定的 Rust 字段 | 不支持的属性无法编译 |
| 伪状态 | 类型化组件状态参与属性表达式 | 不存在隐式优先级 |
| 继承 | 显式传值或组件公开输入 | 不做隐藏继承 |
| 层叠 | 不提供 | 同一属性只有一个明确结果 |
| 自定义变量 | 普通的类型化 Rust 输入 | 输入来源不由 ZUI 决定 |
| 条件规则 | Rust 的 `match` 或类型化约束 | 条件必须穷尽或显式处理 |

ZUI 借用 CSS 易读的声明形式，不复制浏览器的全局选择器、权重计算、隐式继承和层叠覆盖。

## 5. 组件与样式如何配合

样式声明生成角色树和属性类型；组件构建代码把真实节点绑定到这些角色。

```rust
zui::ui! {
    component FilesRow(styles: &FilesRowStyles) {
        row(styles.surface) {
            icon(icon)
            text(styles.surface.label, name)

            row(styles.surface.actions) {
                child RowActions::new(actions)
            }
        }
    }
}
```

绑定时必须满足：

- 角色属于当前组件作用域。
- 节点种类与角色种类一致。
- 子角色只能绑定在其父角色所在子树内。
- 普通角色在一个组件实例中最多绑定一次。
- 需要重复的内容应成为重复实例化的子组件；确实需要局部重复时，角色必须显式声明为 `many`。

样式不是另一棵可以独立渲染的界面树。组件树拥有节点和生命周期，样式树只给命名节点提供受约束的属性。

### 5.1 文件组织

组件行为和组件样式属于同一个组件：

- 小组件默认写在同一文件中，放在相邻区域。
- 当样式声明明显影响组件代码阅读时，只拆出一个相邻的 `style.rs`。
- 不建立覆盖多个功能的全局样式文件，也不按单个属性继续拆分文件。

文件是否拆开不改变作用域。作用域由组件类型决定，不由文件路径决定。

## 6. 节点种类决定属性集合

ZUI 不使用一个包含所有可选字段的巨大 `ElementStyle`。不同节点种类拥有不同样式类型。

| 节点种类 | 允许的主要属性 |
| --- | --- |
| `row` | 宽高约束、间距、内外边距、主轴和交叉轴对齐、伸缩、裁剪、背景、边框 |
| `column` | 与 `row` 相同，但主轴固定为纵向 |
| `grid` | 轨道、行列间距、单元格位置、宽高约束、裁剪、背景、边框 |
| `stack` | 覆盖顺序、对齐、定位、宽高约束、裁剪、背景、边框 |
| `item` | 自身在父布局中的尺寸、伸缩、边距、定位和可见性 |
| `text` | 字体、字号、字重、行高、颜色、换行、截断、选择方式及自身尺寸约束 |
| `image` | 适配方式、采样方式、透明度、圆角及自身尺寸约束 |

`row` 与 `column` 是节点种类，不是可随时被属性改写的方向字段。这样可以避免节点行为、样式声明和布局实现对方向理解不一致。

节点共有属性由内部 trait 复用，但公开接口仍按节点种类暴露，避免出现“字段存在、实际节点却忽略它”的假能力。

## 7. 属性和值

### 7.1 数字字面量

在 `styles!` 内，数字字面量根据属性获得单位和约束：

```rust
row surface {
    height: 24;          // LogicalPx
    gap: 8;             // LogicalPx
    grow: 1;            // Flex
    opacity: 0.92;      // UnitRatio
    padding: [4, 8];    // Insets<LogicalPx>
}
```

这只是宏内的类型推导，不代表所有数字都能互换。`opacity: 24`、`grow: -1`、`height: -8` 等静态非法值必须在编译期报错。

### 7.2 动态值

变量必须已经是目标属性接受的类型：

```rust
row surface {
    height: metrics.row_height;
    gap: metrics.item_gap;
}
```

`metrics.row_height` 应是 `LogicalPx` 或该属性明确接受的 `Length`，而不是裸 `f32`。边界处使用受检查的构造函数：

```rust
let row_height = LogicalPx::try_new(raw_height)?;
```

业务代码不写 `as f32`。只有布局和绘制内部在完成有限值、范围和单位检查后，才能取得底层浮点数。

### 7.3 基本值类型

| 类型 | 约束 |
| --- | --- |
| `LogicalPx` | 有限值；用于尺寸时通常非负 |
| `DevicePx` | 只在设备像素边界使用，不进入组件声明 |
| `Length` | `auto`、逻辑像素、百分比或受支持的布局长度 |
| `Insets<T>` | 一、二或四边值，元素类型一致 |
| `Flex` | 有限且非负 |
| `UnitRatio` | 闭区间 `[0, 1]` |
| `Angle` | 明确单位并规范化 |
| `Duration` | 有限且非负 |
| `Color` | 已解析的颜色值 |
| `FontSpec` | 字体族、字重、字形等明确字段 |

对“通常非负”的属性，约束应落在具体属性类型上，而不是让 `LogicalPx` 本身禁止负数。例如偏移可以为负，宽度不能为负。

### 7.4 初始值

每个属性在 ZUI 中只有一个文档化初始值。未声明属性使用该初始值，不从祖先猜测，也不根据声明顺序寻找上一个值。

同一角色的同一属性写两次是错误，不采用“最后一个生效”。

## 8. 复用与组合

复用使用普通 Rust 函数和完整的类型化值，不使用任意属性映射的拼接。

```rust
fn standard_row(metrics: RowMetrics) -> RowStyle {
    RowStyle::builder()
        .height(metrics.height)
        .gap(metrics.gap)
        .align_items(AlignItems::Center)
        .build()
}
```

设计规则：

- 共享函数返回明确节点种类的完整样式或明确命名的值组。
- 组件仍拥有最终角色和角色树。
- 不允许把 `TextStyle` 片段合进 `RowStyle`。
- 不提供无类型 `HashMap<Property, Value>`。
- 不提供依赖调用顺序的任意 patch 链。

需要局部差异时，优先把差异作为函数参数或在属性位置用 `match` 明确算出。这样阅读某个属性时就能看到它的完整决策，不需要追踪覆盖顺序。

## 9. 状态与变体

状态是组件的类型化输入，样式只负责把状态映射成属性值。

```rust
background: match state.selection {
    Selection::None => colors.row,
    Selection::Selected => colors.row_selected,
};

border_color: match (state.focus, state.validation) {
    (Focus::Visible, Validation::Invalid) => colors.invalid_focus,
    (Focus::Visible, Validation::Valid) => colors.focus,
    (Focus::Hidden, Validation::Invalid) => colors.invalid,
    (Focus::Hidden, Validation::Valid) => colors.transparent,
};
```

ZUI 不定义类似伪类权重的隐式优先级。两个状态同时影响同一属性时，组件必须显式处理组合。Rust 的穷尽检查负责提醒新增状态未被处理。

只改变颜色、边框或透明度的状态触发重绘；改变字号、间距、宽高或可见性的状态触发布局。属性元数据决定失效范围，组件不手写这套判断。

## 10. 布局相关样式语义

样式系统只公开能被布局稳定解释的属性：

- `width`、`height`、`min_*`、`max_*` 定义尺寸约束。
- `grow`、`shrink`、`basis` 定义剩余空间和不足空间的分配。
- `margin`、`padding`、`gap` 使用明确的逻辑像素类型。
- `overflow` 必须显式选择 `visible`、`clip`、`scroll` 或文本专用行为。
- `row`、`column`、`grid`、`stack` 拥有各自固定布局语义。

空间不足不是异常。容器必须根据伸缩、最小尺寸和溢出规则产生确定结果。若约束互相冲突，解析结果应包含可定位的布局诊断，不能产生负尺寸、`NaN` 或无限值。

文本尺寸由真实文本测量参与布局。调用者不传“估算后的文本宽度”。样式可以要求换行或截断，但组件仍负责保留完整内容语义。

## 11. 从声明到界面节点

```text
类型化输入
   ↓
组件样式函数
   ↓
局部角色树与属性值
   ↓
角色绑定校验
   ↓
ResolvedNodeStyle
   ↓
测量、布局、裁剪、绘制与检查信息
```

这条路径只有一次样式解析，不存在第二套运行时选择器结果。

`ResolvedNodeStyle` 是只读结果，并按属性影响分类：

| 分类 | 变化后至少失效 |
| --- | --- |
| 测量 | 文本测量、节点测量、布局、裁剪、绘制 |
| 布局 | 布局、裁剪、绘制 |
| 裁剪 | 裁剪、命中几何、绘制 |
| 绘制 | 绘制 |

布局、裁剪、绘制和命中使用同一份最终几何结果。样式系统不能让其中任意一条路径自行重算另一套尺寸。

## 12. 宏与 builder 必须等价

宏只负责简化书写，不能拥有 builder 没有的能力或更弱的检查。

```rust
let styles = FilesRowStyles::builder()
    .surface(|surface| {
        surface
            .height(24)
            .gap(8)
            .align_items(AlignItems::Center)
            .label(|label| {
                label
                    .grow(1)
                    .shrink(1)
                    .min_width(0)
                    .overflow(TextOverflow::Ellipsis)
            })
    })
    .build()?;
```

两种写法必须生成相同角色类型、相同属性值和相同错误：

- 宏中的未知属性是编译错误。
- builder 中不存在对应方法的属性同样无法表达。
- 宏中的重复属性是编译错误。
- builder 在构建同一属性两次时返回明确错误，而不是悄悄覆盖。
- 动态值经过同一套类型和范围校验。

## 13. 错误边界

### 13.1 编译期错误

以下问题可以仅靠代码结构确定，必须拒绝编译：

- 未知节点种类或属性名。
- 属性不属于该节点种类。
- 同一角色重复声明同一属性。
- 同一作用域重复角色名。
- 跨组件或跨角色分支绑定。
- 角色和真实节点种类不一致。
- 静态数字超出属性允许范围。
- 把普通角色用于重复绑定。

### 13.2 运行期样式错误

动态输入或运算结果可能只在运行期确定。以下问题返回结构化 `StyleError`：

- 非有限数字。
- 动态值超出范围。
- 最小值大于最大值。
- 受检查运算溢出。
- 动态角色集合的键重复。

错误至少包含：

```text
组件实例路径 + 局部角色路径 + 属性 + 输入位置 + 原因
```

一个组件实例的样式解析是原子的。任何角色解析失败时，不提交该组件本帧的部分新样式，也不留下新旧属性混合的结果。

### 13.3 布局诊断

样式本身合法但约束无法同时满足时，布局返回诊断结果并生成确定几何。诊断与 `StyleError` 分开，因为“值非法”和“可用空间不足”不是同一类问题。

## 14. 边界情况

| 场景 | 必须保证的结果 |
| --- | --- |
| 不同组件都有 `label` | 类型和作用域互不影响 |
| 同一组件重复 `label` | 编译失败 |
| 父组件尝试绑定子组件角色 | 编译失败 |
| `text` 写 `align_items` | 编译失败 |
| 普通角色绑定两次 | 编译失败或构建失败，不静默复用 |
| 动态值是 `NaN` 或无限值 | 返回 `StyleError` |
| 有限值经过运算溢出 | 受检查运算失败 |
| 容器宽高为零 | 产生零面积确定布局，不崩溃 |
| 固定尺寸总和超过可用空间 | 按伸缩和溢出规则处理并可诊断 |
| 超长英文、中文、emoji、组合字符或双向文本 | 使用同一文本测量与截断路径 |
| 多个状态同时影响属性 | 由显式 `match` 决定唯一结果 |
| 动态列表有十万项 | 样式解析不把数据项展开成全局选择器表 |
| 动态输入频繁改变 | 只使受影响的解析、布局或绘制失效 |
| 插入无名实现容器 | 不改变局部角色路径 |
| 命名节点移到另一命名分支 | 绑定检查失败，要求显式调整 |

## 15. Rust 接口约束

- 公开样式接口使用准确的领域类型，不公开裸浮点字段。
- 角色类型携带组件作用域、父角色和节点种类信息。
- 节点种类用不同结构体表达，不用大量 `Option` 模拟。
- 静态样式尽可能成为只读常量；动态样式返回不可变结果。
- 构建、解析和检查不依赖全局可变状态。
- 不使用字符串反射实现正常渲染路径。
- 调试路径可以生成字符串，但字符串不能反过来获得修改权限。
- 宏展开后的代码应能被普通 Rust 工具定位到原始属性位置。
- 样式函数可单独测试，不要求启动窗口或绘制设备。

## 16. 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| 完整实现 CSS | 引入全局匹配、权重、继承和大量运行时复杂度 |
| 全局类型化选择器 | 虽然没有字符串，但仍允许远处代码穿透组件边界 |
| 祖先路径选择器 | 组件内部调整会让外部样式失效，归属也不清楚 |
| 巨型 `ElementStyle` | 大量无效字段组合只能拖到运行期发现 |
| 任意 patch 和最后写入生效 | 属性结果依赖调用顺序，难以阅读和诊断 |
| 宏和 builder 两套规则 | 同一界面换一种写法就得到不同结果 |
| 业务层到处写 `as f32` | 单位、范围和非有限值无法在边界处统一检查 |
| 运行时字符串角色 | 拼写和跨组件错误被拖到运行期 |
| 样式树拥有节点生命周期 | 会与组件树形成两个互相竞争的界面结构 |

## 17. 与当前实现的差距

当前 ZUI 已有声明式元素、`style!`、`ui!`、基础 `ElementStyle` 和部分校验能力，但还没有达到本文设计：

- 样式角色尚未完整携带组件作用域、父角色和节点种类。
- 样式声明与真实节点树还不能验证跨分支绑定。
- 节点种类与属性集合仍有重叠，非法组合仍可能进入运行期。
- 宏和 builder 的能力与错误行为尚未完全一致。
- 数值边界仍能看到裸 `f32` 和显式转换。
- 重复属性、动态范围、约束冲突的诊断信息还不统一。
- 检查信息还不能稳定显示完整组件实例路径与局部角色路径。

本文只确定目标模型和边界，不在这里给出现有代码的迁移顺序或兼容层方案。

## 18. 验收标准

设计落地后，应能通过以下结果判断，而不是只看示例能否编译：

- 可以从任意命名节点追溯完整组件归属和局部角色路径。
- 父组件无法读取或绑定子组件的私有角色。
- 相同角色名在不同组件中不会冲突。
- 未知属性、重复属性、跨节点种类属性和跨分支绑定尽量在编译期失败。
- 宏与 builder 对同一输入产生完全相同的已解析样式和错误。
- 业务代码用数字字面量或明确单位类型，不需要写 `as f32`。
- 非有限值、范围错误和受检查运算错误有稳定、可定位的结果。
- 多状态组合没有隐藏优先级，同一输入始终得到同一属性结果。
- 长文本、极窄空间、零尺寸和超大有限输入不会产生非法几何。
- 样式变化按属性类别触发最小且正确的失效范围。
- 正常构建和绘制路径不执行字符串选择器匹配。
