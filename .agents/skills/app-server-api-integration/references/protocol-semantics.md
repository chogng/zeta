# 协议语义

设计请求、通知、订阅、流、取消、服务端发起请求、错误、并发或重连时，完整读取本文件。

## 先写协议对照

在编码前为一次真实行为回答：

| 项目 | 必须明确 |
| --- | --- |
| 调用方契约 | 哪个现有 TypeScript 接口被调用，返回值和可观察副作用是什么 |
| Rust owner | 哪个领域校验输入、决定行为并产生结果 |
| 消息形态 | 一次性请求、全连接通知、资源订阅、流还是服务端发起请求 |
| 生命周期 | 谁创建、谁释放，连接断开、窗口关闭或对象销毁时如何结束 |
| 取消 | 取消哪项 Rust 工作，何处观察取消，最终响应与事件是什么 |
| 顺序与并发 | 哪些可并行，哪些按 workspace、session、terminal、watch 或资源版本串行 |
| 失败 | 领域错误如何进入协议，adapter 如何恢复成已有前端错误 |
| 重连 | 哪些状态可恢复，使用持久标识、重放、重新订阅还是明确失败 |
| 兼容性 | 协议版本、生成类型和能力协商如何证明两端匹配 |

## 选择消息形态

### 一次性请求

使用有类型的 request/response，方法名按 `domain/action` 组织。不要设计 `invoke(method, unknown)`。响应必须区分成功、领域错误、连接终止和取消。

### 全连接通知

连接初始化后，Rust 可以在整个连接生命周期内发送全局通知。TypeScript 本地监听器的增减不等于 Rust 资源的 start/stop；连接 owner 统一分派这些通知，并在连接关闭时结束。

Codex initialize 中的通知能力协商可作为连接级机制的参考，但不能替代具体领域生命周期。

### 资源订阅

watch、持续诊断和其他按资源创建的订阅使用稳定标识、显式 start/stop，以及携带该标识的通知。最后一个拥有该资源的前端对象释放时，adapter 必须停止 Rust 资源。

Codex 文件协议中的 watch/unwatch 可作为资源级机制的参考。不要把所有通知都误建成订阅，也不要让资源订阅活到连接结束才清理。

### 流

流协议包含稳定流标识、单调序号、终止状态和缺口语义。大数据还需定义分块上限、背压和取消。不要把无限通知伪装成普通 Promise，也不要假设通知永不丢失或永远有序。

### 取消

VS Code `CancellationToken` 必须映射为 Rust 明确支持的 cancel、interrupt 或 session stop。只丢弃 TypeScript Promise 不构成取消。定义取消与正常完成并发时谁获胜，以及取消后是否仍允许终止通知。

不要假设 JSON-RPC 自动提供任意请求取消；每个可取消领域行为都要有 Rust 可观察的取消点。

### 服务端发起请求

Rust 需要前端响应时，使用带请求编号的有类型 request，并定义 response、error、超时、取消和连接关闭语义。不要用一条通知加另一个命令模拟回复。

### 变更、并发与幂等

需要安全重试的变更使用幂等键、revision 或领域稳定标识。序列化范围由协议明确表达，不能依赖前端调用时机碰巧有序。跨资源可并行时避免用整条连接的全局锁制造无关阻塞。

### 错误

线上错误保留稳定类别和必要字段，adapter 再转换为 VS Code 已有错误。不要靠英文消息文本判断错误种类，也不要把 Rust 内部错误结构直接暴露给产品代码。

### 重连

新连接重新执行 initialize、版本和能力协商。所有旧 pending requests 明确失败；旧连接通知按连接代次丢弃。资源订阅、流和终端会话只有在协议明确支持恢复时才重建，否则向现有前端契约报告终止。

## 协议验证

- schema 或生成测试证明 Rust 定义能够稳定生成 `zeta-ts/generated/app-server/types.ts`。
- 双端测试覆盖请求关联、通知分派、资源 start/stop、流终止、取消竞争、服务端请求回复和连接关闭。
- 错误测试证明 Rust 错误可恢复成调用方已经处理的 VS Code 错误类别。
- 重连测试证明旧响应和旧通知不会污染新连接，且只恢复协议承诺可恢复的资源。
- `rg` 检查方法名、DTO、pending map 和 framing 没有在多个领域 adapter 中重复实现。
