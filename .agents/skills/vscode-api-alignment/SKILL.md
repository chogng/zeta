# VS Code TypeScript API 对齐

以 `../vscode/src/vs` 为只读参照，让 Zeta TypeScript 中明确对应 VS Code 的文件、公开契约、职责和真实调用链可以逐项定位。上游只用于确认结构和可观察行为；实现与测试必须由 Zeta 独立编写，禁止复制、批量同步、逐行翻译或轻微改写上游代码。

## 路由

先按目标文件所在层读取对应 reference；一项任务修改多层时读取所有涉及层，不加载无关层：

| Zeta 范围 | 必须读取 |
| --- | --- |
| `zeta-ts/src/zeta/base` | [Base 对齐](references/base.md) |
| `zeta-ts/src/zeta/platform` | [Platform 对齐](references/platform.md) |
| `zeta-ts/src/zeta/editor` | [Editor 对齐](references/editor-example.md) |
| `zeta-ts/src/zeta/workbench` | [Workbench 对齐](references/workbench.md) |
| `zeta-ts/src/zeta/code` | [Code 对齐](references/code.md) |
| `zeta-ts/src/zeta/sessions` | [Sessions 对齐](references/sessions.md) |

Rust 文件不使用本 skill，也不以 VS Code 为参照。普通 TypeScript 命名若没有 VS Code 对应关系，同样不使用本 skill。

## 对比规则

文件和公开 API 使用同一条非对称规则。先批量完成整个目标目录的对比，再按下表行动：

| 对比结果 | 行动 |
| --- | --- |
| VS Code 有，Zeta 没有 | 直接补齐对应文件或公开 API，并同步职责、调用方和测试。 |
| 双方都有 | 对齐路径、公开契约、职责、生命周期和可观察行为；内部实现由 Zeta 独立设计。 |
| Zeta 有，VS Code 没有，且尚无用户决定 | 暂停修改并一次性报告完整清单，由用户决定保留、改名、迁移或删除。 |
| Zeta 有，VS Code 没有，且已有用户决定 | 按已记录的决定处理；确认作为 Zeta 专属归属的文件或 API 可以继续承接其职责。 |
| 只有内部实现不同 | 不要求同名或同算法，只验证职责边界与可观察行为。 |

“公开 API”包括跨文件使用的导出、公开成员、服务契约、注册标识、配置键和回调契约，不包括只在文件内部使用的私有辅助代码。用户对仅 Zeta 文件或 API 作出决定后，将路径、确认职责和处理方式写入当前对齐台账；除非职责、公开契约或调用方发生变化，后续批次不重复询问。

文件是否存在于 VS Code 只决定是否需要用户确认，不决定 Zeta 的最终职责归属。VS Code 对应职责必须回到对应路径；Zeta 专属职责应回到用户已确认且符合仓库依赖方向的 Zeta 专属归属，即使 VS Code 不存在该文件。目标归属尚不存在时，必须先提交拟新增路径和职责供用户决定，确认后才能创建。一个文件混合两类职责时，只迁移对应职责，不为文件数量机械搬运全部实现。

## 对齐不变量

- 对应实现使用准确的相对路径、文件名、大小写、公开名称、签名和 owner 模块。文件拆分、状态 owner、生命周期、调用顺序、副作用和错误语义都属于契约；只对齐导出或成员名属于假对齐。
- VS Code 存在而 Zeta 缺失的生产文件和公开 API 都属于待补项，不以文件数量、成员数量或类型检查结果代替实现。
- 同一运行环境和生产调用路径中的一个公开职责只能有一个入口、一个实现和一个状态 owner。现有 Zeta 实现已承担对应职责时，直接迁移或重命名该实现并同批更新全部调用方；不得新增同名外壳、继承外壳、转调类、别名、聚合导出或新旧 API 并存。
- 只有运行环境、职责、输入语义或生命周期确实不同才拆开实现；多个公开契约共享同一机制时，共享逻辑仍只保留一份并由正确层拥有，不能复制实现或状态。
- VS Code 不是内部设计上限。满足对应职责和可观察行为后，保留或改进更简单、清晰且适合 Zeta 的数据结构和控制流，不为形似上游增加无用状态、分支或抽象。
- 遵守 `base → platform → editor → workbench → code` 的依赖方向；`sessions` 可以依赖 `workbench` 及更低层，`workbench` 不得依赖 `sessions`。`common` 不引入浏览器、Node 或 Electron 环境能力。
- 发现仓库已有上游实质代码时，保留其许可证与来源信息并停止扩散；不得删除许可证头来伪装成本地实现。

## 同路径批量调查

用户指定目录或同一目录下多个文件时，把完整目录当作一个查询批次。首次只读检查应批量取得：

- 本地与上游的生产文件集合、同路径、仅本地、仅上游和大小写差异；
- 对应文件的 imports、exports、公开声明和直接生产调用方；
- 上游直接调用方、相关测试以及本地现有行为测试。

优先使用一次目录审计、带多个模式的 `rg`、循环读取或等价批量工具。输出过大时按“文件集合”“符号与调用方”“测试”拆批，不能默认退化为逐文件查询。批量调查不扩大修改或删除权限。

## 工作流程

1. 修改前保存 `git status --short`、tracked diff 和未跟踪文件清单，区分任务创建、用户已有和来源不明的改动；来源不明默认保护。
2. 读取涉及层的 reference，确定本地根目录、VS Code 根目录、目标目录、必要调用方和层级验证入口。
3. 建立对应表，记录文件与公开 API 是“双方都有”“仅 VS Code”还是“仅 Zeta”，以及符号路径、owner、职责、调用链、生命周期和行为差异。
4. 把上游 imports 当作依赖能力清单，沿缺失或错误 owner 深度优先追踪；一条依赖分支未闭合前，不铺开不相关分支，也不添加临时桥接文件。
5. 从真实用户行为、上游测试或缺陷路径核对触发点、状态变化、坐标语义、副作用、错误与释放顺序。
6. 先把现有实现和状态收敛到唯一 owner，再统一路径、名称、参数、返回值、枚举、配置键和回调契约。
7. 同批更新必要调用方、测试和当前架构文档；用定向行为测试证明本地实现，不把类型检查当作完成证据。

当本地一个文件承担上游多个文件的职责时，把 VS Code 对应职责迁回准确 owner；Zeta 专属职责迁回已确认的 Zeta 专属 owner。发现尚未记录决定的仅 Zeta 文件或公开 API 时，完成本批只读清单后暂停并请求用户决定，不能自行保留、改名、迁移或删除；已有决定的项目按记录继续处理。

## 删除确认

任何文件删除都必须在执行前取得用户对准确路径清单的确认。清单需要说明删除原因、VS Code 对应情况、剩余生产调用方数量和 Git 可恢复性。目录、glob 或此前的概括授权不能替代本次确认；清单变化后必须重新确认。

等待确认期间可以继续不改变候选及其调用链的只读调查，但不能删除、移动隐藏文件或继续实施依赖该删除决定的修改。

## 验证

- 修改前后重新比较完整目标目录；仅 VS Code 的文件和公开 API 应减少，新出现且尚无决定的仅 Zeta 文件或公开 API 必须暂停并请求用户决定，已有决定的 Zeta 专属归属必须符合其确认职责。
- 逐项复核 imports 的符号和 owner 路径，并用 `rg` 检查旧名称、错误大小写、别名、重复入口、并行实现和聚合导入。
- 确认旧公开入口和旧状态 owner 已无生产调用方，新的公开契约实际走向唯一现有实现，而不是新增一份实现。
- 至少验证一条受影响的真实行为链，覆盖触发、owner、状态变化、副作用和释放。
- 优先运行仓库定义的最小类型检查和能够直接触发受影响职责的定向行为测试。结构审计、成员名比较和类型检查都不能代替行为测试；报告必须列出实际运行的测试及其覆盖行为。检查配置必须禁止输出，生成产物的构建或测试配置必须把 `outDir` 放在源码树外。
- 最后复核对应表、`git diff` 和 `git status`，分别报告真实对齐、仍是假对齐、缺失 owner、范围阻塞和未解决验证失败。
