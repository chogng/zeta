# 进程资源采样设计

- 本文说明采样需求、后台线程、读数版本和有界历史的职责。
- 显示字段、采样周期和统计口径以[状态与资源规格](../spec/status.md)为准。
- 用户主动启动的持续诊断由[共享内存诊断](../../../zeta-rs/docs/memory-diagnostics.md)负责；TUI 接入见[诊断规格](../spec/memory-diagnostics.md)。

## 数据路径与职责

| 顺序 | 负责人 | 输入与输出 |
| --- | --- | --- |
| 1 | 状态行排版、`StatusPanel` | 报告实际可见资源项、当前页签和正文空间 |
| 2 | 应用排版与事件循环 | 合并可见条件，生成唯一需求；不能执行阻塞系统调用 |
| 3 | 事件泵 | 分配递增需求版本，传给 Host，将结果送回状态更新循环 |
| 4 | `ProcessResourcesSource` | 按需求读取当前 TUI 和明确 PID 的本地 App Server 进程树，不猜测角色或修改 UI |
| 5 | `RuntimeQueue` | 同版本只保留尚未处理的最新读数；旧版本不能覆盖队列中的新版本 |
| 6 | `ProcessResourcesModel` | 丢弃旧版本，聚合读数，维护有界历史并生成显示快照 |

## 需求与线程生命周期

| 事件 | 处理 |
| --- | --- |
| 事件泵创建 | 建立一个长期存在的采样工作线程，默认阻塞等待需求 |
| 配置、尺寸、面板或页签变化 | 重新计算需求，选择最完整指标和最短周期，分配新版本 |
| 没有可见需求 | 阻塞等待，不定时唤醒；释放系统进程缓存和 CPU 基线 |
| 开始观测 | 立即读取；CPU 在第二个时间点才可计算 |
| 需求降级 | 保留仍请求指标的有效状态，停止其余指标及对应统计周期 |
| 指标停止后重现 | 可保留最后值用于稳定排版，但新周期重置状态，不展示成新采样值 |
| 线程创建或采样失败 | 生成不可用状态，核心终端生命周期继续运行 |

- 一个线程服务需求切换，避免切页时反复创建线程。
- 绘制函数只读状态，不能启动、停止或修改采样器。
- 需求版本与读数版本必须一致；输入繁忙也不能积压资源事件。

## 历史与失败边界

- 历史按容量和时间裁剪，最多 301 个内存合计样本。
- 峰值和趋势属于连续内存观测周期；结束时清除，恢复后不连接未采样间隔。
- 进程身份与本机合计规则由[规格](../spec/status.md#本机进程的范围)决定；缺失必要读数时不能制造完整合计。
- 资源观测不拥有诊断会话、告警或泄漏结论；持续诊断不能随面板隐藏而停止。

## 验证要求

| 类别 | 检查内容 |
| --- | --- |
| 需求计算 | 停止、简要、详细及合并优先级；宽度变化和 Thread/Processes 切页 |
| 停止与恢复 | 停止无进程刷新和事件；恢复内存立即可读、CPU 首次 collecting |
| 统计周期 | 未采样间隔不进入峰值与趋势；固定容量和时间裁剪 |
| 失败 | 读取或线程失败不阻断 TUI，不产生不完整合计 |
| 进程树 | 子进程稳定层级排列，正确进入 App Server 与本机合计 |
| 版本与队列 | 旧版本丢弃，高频输入时只保留最新有效读数 |

- 持续诊断的斜率、空闲基线、导出和停止清理测试由共享后端维护，见[诊断验收](../../../zeta-rs/docs/changes/memory-diagnostics/verification.md)。
- 短时测试不能用“内存没有上涨”证明不存在泄漏；本次文档整理没有重新执行产品测试。
