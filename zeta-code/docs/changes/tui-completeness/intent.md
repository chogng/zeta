# TUI 功能完整性：目标

用户应该能在终端里完成一次完整的 Agent 工作：开始任务，提供上下文，查看过程，在需要时批准、补充或中断，最后取得结果；离开后还能找到并继续原来的会话。

这次梳理要让你看清：上述流程要求什么、当前缺什么，以及凭什么判断它已经完成。

## 为什么现在要梳理

目前的文档分别描述布局、按键、架构和源码，却没有连成完整的用户流程。一个命令或面板存在，不代表它的失败、返回、恢复和后续操作都已做完。只有模板和目录，也无法帮助你发现这些漏项。

需求来自本任务中你提出的两个问题：“无法准确发现自己要开发的功能是否完备”和“现在需要看得懂，看明白”。你已同意先补齐这项梳理的四份正文。本文件是当前目标的整理，不补写旧功能的历史批准记录。版本：v1，2026-09-07。

## 用户最终应该能完成什么

- **开始和推进任务**：输入文字或图片，选择上下文，提交、排队、补充和中断；遇到批准或提问时作出明确回应。
- **管理和继续工作**：找到会话，预览、切换、分支、回退、归档和恢复；操作结束后回到正确位置。
- **读懂结果并保持可用**：阅读长输出、复制或导出，修改必要设置，处理连接失败，正常退出终端。

这些目标覆盖现有 TUI 的主要用户流程。模型、工具和权限决定继续通过共享后端执行；本次不重新设计后端协议或桌面界面。

## 本轮要交付什么

[规格](spec.md)把目标写成可观察的操作结果；[计划](plan.md)列出检查与补齐顺序；[验收](verification.md)逐项记录已知实现、证据和未完成处。首页应能直接打开这四份正文。

本轮先建立可审阅的功能基线。产品本身是否完整，需要后续执行规格中的验收；文档写完不能代替产品通过。

## 怎样判断梳理有用

你不需要先理解 Rust 类型或文件树，就能指出某个流程缺了哪个步骤。每条要求都能在计划中找到下一步，在验收中找到结果或明确的未知项。缺少证据的地方不能写成通过。

Markdown 支持程度、必测终端组合、断线后的未发送内容，以及已有装饰性功能的交付范围，集中列在[规格末尾](spec.md#尚需确定的完成边界)。它们没有默认答案，不能根据当前代码反推用户一定接受这些限制。
