# 进程资源观测与内存诊断

> 本文由 `zeta-code` 产品拥有，固定 TUI 进程资源观测的用户语义、采样生命周期和内存诊断边界。当前 TUI 的状态、事件与 Host 责任见 [TUI 架构](tui.md)，界面位置与字段见[界面部位词典](LAYOUT.md)。按需观测已经实现；内存诊断仍是潜在方向。

## 快速理解

进程资源信息只在用户能够看到它时才值得持续采样；内存泄漏诊断则是另一项需要用户明确启动、持续收集证据的能力。默认观测不会在后台承担告警职责，也不会把常驻内存上涨直接解释成泄漏。

| 场景 | 当前行为 | 状态 |
| --- | --- | --- |
| 状态行显示内存或 CPU | 每 2 秒只采状态行实际显示的指标 | 已实现 |
| `/status` 的 Processes 页可见 | 每秒采样完整进程信息 | 已实现 |
| `/status` 的 Session 页可见 | Session 页本身不提出资源观测需求 | 已实现 |
| 两处都没有显示资源信息 | 停止读取进程数据，采样线程进入休眠 | 已实现 |
| 用户排查疑似内存泄漏 | 尚无专用诊断能力；未来由显式诊断会话持续采样并导出证据 | 潜在方向 |

后续章节依次说明[用户可见语义](#1-用户可见语义)、[按需采样](#3-已实现需求与生命周期)、[内存诊断边界](#5-潜在方向内存诊断)和[当前实现证据](#7-当前实现与证据)。

## 1. 用户可见语义

状态行提供快速读数，Processes 页提供本机合计、TUI、本地 App Server 进程树、观察到的内存峰值以及 1 分钟和 5 分钟变化。App Server 先显示包含全部子进程的合计，再显示主进程和按父子层级排列的子进程；LSP 与其他由 App Server 启动的进程都使用操作系统进程名展示，不靠命令参数猜测角色。内存使用常驻内存口径；CPU 表示进程占本机逻辑 CPU 总容量的比例。

资源观测只覆盖身份明确且由产品直接拥有的本机进程：

- 当前 TUI 进程始终属于本机合计；
- CLI 明确登记 PID 的本地 App Server 及其全部后代进程单独采样并计入合计；
- 进程内 App Server 已包含在 TUI 进程读数中，不能重复相加；
- 远程 App Server 明确排除在本机合计之外；
- 不属于本地 App Server 进程树的工具进程不计入任何一项。

读取失败、目标进程退出或系统不支持时显示 `unavailable`。CPU 需要两个时间点才能计算，开始一段新的观测周期后首次显示 `collecting`。

## 2. 已实现：按需观测

`ProcessResourcesSource` 随事件泵建立一个后台工作线程，但默认阻塞等待，不读取任何进程数据。应用层根据当前排版和 Status 面板页签生成唯一观测需求；状态行按 2 秒周期只请求实际显示的指标，Processes 页按 1 秒周期请求完整信息。

每次需求变化都生成递增版本。采样读数携带对应版本，`ProcessResourcesModel` 忽略晚到的旧版本；`RuntimeQueue` 也不允许旧版本覆盖已经排队的新版本。队列对同一版本只保留尚未处理的最新读数，避免终端输入繁忙时积累资源事件。

资源观测线程创建失败、系统接口不支持或读取失败时，界面显示不可用，TUI 核心生命周期继续运行。

## 3. 已实现：需求与生命周期

### 3.1 需求等级

应用层统一计算当前资源观测需求，界面只报告自己需要显示什么，Host 只执行采样。多个可见条件同时成立时，取最完整的指标集合和最短的采样周期。

| 需求等级 | 触发条件 | 周期 | 指标 |
| --- | --- | --- | --- |
| 停止 | 没有可见消费者 | 无 | 不读取进程数据 |
| 简要 | 状态行实际排入内存或 CPU 项 | 2 秒 | 只采实际排入的指标 |
| 详细 | Processes 页是 Status 面板当前页签且有正文显示空间 | 1 秒 | 内存、CPU、峰值和趋势所需数据 |

“实际排入”以状态行当前获得的行数和宽度经过排版选择后的结果为准，不以配置中是否启用为准。终端调整大小、状态行配置变化、Status 面板开关和页签切换都会重新计算需求。绘制代码保持纯显示职责，不能直接启动、停止或修改采样器。

### 3.2 生命周期

事件泵拥有一个长期存在的采样工作线程，并向它发送最新需求。工作线程在停止状态阻塞等待，不进行定时唤醒；同时释放系统进程缓存和 CPU 计算基线。这样避免频繁切换页签时反复创建线程，停止期间也不产生采样事件。

需求从停止变为简要或详细时立即进行第一次读取。内存可以在第一次读取后显示，CPU 在获得下一次读数前保持 `collecting`。需求降级时保留仍被请求指标的有效状态；指标停止采样时保留最后读数以稳定后续排版，但不会在不可见处绘制，并立即结束对应统计周期。指标重新进入可见区域时先重置为 `collecting`，不能把保留值冒充新周期读数。

### 3.3 统计周期

峰值和趋势只能描述有连续样本覆盖的观测周期：

- 内存首次成为所需指标时开始内存观测周期；
- 状态行与 Processes 页之间切换不会中断仍在持续采样的指标；
- 没有任何界面需要内存时结束该周期，并清除峰值与趋势历史；
- 重新开始后不能跨越未采样时段计算 1 分钟或 5 分钟变化；
- 固定容量和时间裁剪继续把历史限制在最多 301 个样本。

界面中的“观察峰值”必须始终指当前连续观测周期，不能暗示进程全生命周期峰值。

## 4. 已实现：责任边界与失败语义

| 负责人 | 决定或执行什么 | 不能负责什么 |
| --- | --- | --- |
| 状态行排版 | 根据配置、数据和宽度决定实际显示的资源项 | 控制采样线程 |
| `StatusPanel` | 暴露当前页签是否为 Processes | 读取操作系统进程数据 |
| 应用排版与事件循环 | 合并所有可见条件，产生唯一观测需求；把当前请求安装到显示模型 | 执行阻塞式系统调用 |
| 事件泵 | 为需求分配版本，把请求传给 Host，并把最新读数送回单写者循环 | 解释峰值、趋势或泄漏 |
| `host/process_resources.rs` | 按需求刷新 TUI，以及明确 App Server PID 为根的进程树，并在停止时休眠 | 根据命令参数猜测子进程角色或修改 UI 状态 |
| `status/resources.rs` | 聚合读数，维护有界历史，生成显示快照 | 决定采样时机 |

资源观测属于附加信息。线程创建失败、系统接口不可用或单次读取失败都会使指标进入不可用状态，不会阻止 TUI 启动、输入、对话或退出。某个应计入合计的本地进程不可读时，本机合计也显示不可用，不把不完整数值伪装成完整合计。

## 5. 潜在方向：内存诊断

内存诊断只有在出现真实排查需求时才实现，并作为用户明确启动和停止的独立诊断会话。它不受界面可见性控制，因为持续观察本身就是用户请求；默认资源观测不能暗中升级为后台诊断。

一套可信的诊断会话至少需要：

- 以约 5 秒的低频周期分别采集 TUI 和本地 App Server；
- 使用固定容量缓冲区，保证诊断自身的内存占用有上限；
- 观察 10～30 分钟增长斜率，而不是比较相邻两个样本；
- 重点比较任务结束或进入空闲后的稳定基线是否持续抬升；
- 导出时间戳、进程角色、常驻内存和 CPU 时间序列，且不包含命令参数、环境变量或对话内容；
- 会话结束或 TUI 退出时可靠停止，不留下后台工作。

诊断结果只能描述“疑似持续增长”及其证据，不能仅凭常驻内存曲线宣称发生泄漏。Rust 分配器保留、缓存、会话历史和共享内存统计都可能使常驻内存增长；定位泄漏仍需对可疑进程使用堆分配分析工具，把增长关联到具体分配来源。

诊断入口、导出格式和平台分析工具尚未确定，不构成当前公共命令或兼容性承诺。

## 6. 验证要求

按需采样由单元测试验证：

- 三种需求等级及合并优先级；
- 状态行项目因宽度加入或退出后，观测需求随之变化；
- Session 与 Processes 页签切换正确启停详细采样；
- 停止期间没有进程刷新和资源事件；
- 恢复后内存立即可用、CPU 首次为 `collecting`；
- 未采样间隔不会进入峰值和趋势计算；
- 读取失败不会中断 TUI，且不产生不完整合计；
- App Server 子进程按稳定层级排列并进入 App Server 与本机合计；
- 高频输入下资源事件仍只保留最新值。

只有在诊断能力进入实现阶段后，才增加长时间斜率、空闲基线、有界存储、导出内容和停止清理测试。短时单元测试不能用“内存没有上涨”证明不存在泄漏。

## 8. 长期不变量

- 默认资源观测没有可见消费者时不采样。
- 只有当前 TUI 和明确 App Server PID 为根的本机进程树进入合计。
- 远程资源不混入本机读数，缺少局部读数时不制造完整合计。
- 采样和历史始终有固定成本上限，资源事件不能无限积压。
- 可选的观测失败不能影响 TUI 核心交互生命周期。
- 常驻内存趋势只能作为诊断线索，不能单独成为内存泄漏结论。
